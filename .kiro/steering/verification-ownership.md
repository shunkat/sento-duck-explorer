# 検証の担当と結果の再利用

2026-11-20、ユーザーは別セッションとKiroの検証重複を減らすよう依頼した。この文書を検証分担の正とし、以前の「Crewが通常操作を検証」「Webが毎回ブラウザーを検証」という指示を以下へ更新する。受入条件や独立レビューは省略しない。

## 通しプレイは修正一式の最後に1回

同日の追加指示「全体の修正が終わったら1度だけ実施する」に従う。修正途中は必要な自動テストと独立コードレビューで進め、今回依頼された修正一式と必須指摘の対応がすべて揃った固定版で、最後に1回だけ通常入力の通しプレイを行う。以前の「全ルートに影響する変更なら、その変更ごとに通しプレイ」という方針は撤回する。

- Conductorと監督は今回まとめて直す項目を一覧化し、個別コミット・個別指摘・小機能の完了ごとに実プレイへ引き渡さない。移動・水域・受け渡し・進行の変更も、修正一式の最終確認にまとめる。小修正ごとに別の修正一式と呼び替えない。
- 途中のブラウザー操作は、原因調査に不可欠な場合の該当箇所の短い再現確認に限る。一般的な安心確認や自動テスト成功のたびの実プレイは行わない。最終確認まで未実施の項目は「最終確認待ち」と残し、実装を止めたり成功扱いしたりしない。
- 最終確認ではクリアルートを1回通し、必要な失敗条件・復元・表示の局所確認も同じ検証枠にまとめる。不具合が見つかった場合は修正後に該当箇所だけを確認し、途中で止めた場合は未確認の残りを続ける。毎回スタートからの全ルート再走を自動追加しない。結果には対象版と確認範囲を正確に残す。

## 担当を一つにする

| 担当 | 実施すること |
| --- | --- |
| Crew A | 実装、必要な自動テスト・ビルド・公開検査。対象コミット、コマンド、結果、残課題をまとめて渡す |
| Crew B | 受入条件と差分の独立レビュー、Aの検証範囲と結果の確認。必要な自動検証を追加し、実プレイ項目は修正一式の最終確認へまとめる |
| 既存のCodex実装監督セッション | 修正一式が揃った後の1回の通しプレイとその結果の記録。素材制作と公開前の確認も引き続き担当する |
| Crew Conductor | 作業ごとの担当・対象コミット・検証範囲と引き渡しを管理し、同じ作業を別担当へ重ねて依頼しない |
| Kiro Web | PR #1〜#3のレビューと各PR内の修正・必要な検証。Crew/PR #4の実装や通常入力の通しプレイを重複して開始しない |

- 同じ版の全テスト・ビルド・通しプレイを、A、B、Codex、Webが順番に一式やり直す運用にしない。Bは自分でコードと受入条件を評価する。実行しなかった検証を「再実行成功」と書かない。
- Codexの追加コードレビューは、Bの未解決指摘、Bが確認できない専門領域、Bの中断を補う場合に限定する。同じ差分へのレビュー担当を理由なく増やさない。
- ブラウザー検証がWeb/Crewに必要な場合は、目的と不足するシナリオを最終確認の一覧へまとめる。原因調査の局所再現を除き、修正途中には実施しない。担当を移す場合は現担当の操作終了と引き渡しを確認してから始める。ツールを使えることだけを再検証の理由にしない。

## 引き渡しと固定

1. Aは修正一式を実装し、必要な自動テスト・ビルドとローカルコミットを完了してBへ差分・結果・残課題を渡す。Bの必須指摘はまとめて修正し、必要な自動検証と再レビューを行う。個別修正の完了だけでは実プレイへ引き渡さない。
2. 修正一式と必須指摘の対応がすべて揃った時点で、Conductorと担当が担当名・ブランチ・固定コミット・最終確認の一覧・サーバーを確認し、1回の通しプレイへ引き渡す。PR #4の実プレイ担当は既存のCodex実装監督セッション。別の最適化・調査セッションはブラウザーを操作しない。
3. 実プレイ中は対象worktreeのソース、素材、依存関係、文書、HEADと開発サーバーを固定する。他担当はそのworktreeの編集、checkout/merge、npm ci、ビルド、再起動、ブラウザー操作をしない。検証中の指摘は私用の引き渡し記録へ残し、担当の停止確認後に直す。
4. 他の許可済み作業を進める場合は、検証対象へ影響しない別worktree・別サーバーを使い、同じ機能を重複実装しない。新規の並列担当や監視ループを、この分担整理だけを理由に増やさない。
5. 実プレイ担当は完了・中断・残課題を返して操作権を解放する。検証結果の文書化とpush前確認は引き渡し後にまとめる。結果待ちだけの自動goal・ナッジを回し続けない。

## 再検証する範囲

| 変更・状況 | 検証 |
| --- | --- |
| 文書・担当指示だけ | 差分・参照先・公開検査。ゲームのテスト、ビルド、実プレイは繰り返さない |
| 修正途中の表示・入力・ロジック変更 | 必要な自動テストと独立レビュー。実プレイ項目は最終確認の一覧へ追加する |
| 修正途中の移動、水域、受け渡し、進行など広い変更 | 必要な自動回帰と独立レビュー。変更ごとの通しプレイは行わず、修正一式の最後へまとめる |
| 修正一式と必須指摘の対応がすべて完了 | 固定版で1回の通しプレイと、一覧化した失敗条件・復元等の局所確認を行う |
| 原因調査にブラウザーが不可欠、または最終確認で不具合を発見 | 該当箇所の再現・修正後の局所確認だけを行う。通しプレイを自動追加せず、未確認範囲は明記する |

- 実行記録は対象コミット、実行者、日時、対象範囲、結果、未実施範囲を残す。自動テスト、独立レビュー、通常入力、状態注入を区別する。
- 別コミットへ結果を引き継ぐときは、元の検証コミットを維持し、ソース・素材・依存関係・ビルド設定・実行環境の差と影響を確認する。根拠なく新しい版で実行済みとしない。
- PR #4の版別実績は同ブランチの `docs/shoulder-view-verification.md` を参照する。mainや古いSpecの未チェック項目だけを見て既存の通しプレイを再依頼しない。未マージの実績をmainで確認済みとも扱わない。
- 例えば水上移動を変えた版へ、変更前の全ルート成功をそのまま流用しない。実行結果は担当が記録する。

この分担は検証の重複を減らすためのもので、未実装・不具合・未確認の受入条件を完了扱いするものではない。マージ、デプロイ、提出、権限、課金について既存の許可範囲は変えない。
